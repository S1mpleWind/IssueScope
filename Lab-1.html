1学习产出#

完成本实验后，应当能够：

  1. 使用 GitHub 规则集为主干设置合并门禁（下文称 merge gate）：改动只能通过 PR 进入 main，且须经组员审批、CI 通过。
  2. 使用 GitHub Actions 搭建“提交 → 构建 → 测试 → 打包”的流水线，验证测试失败时合并被阻止、修复后放行。
  3. 使每个制品携带版本号、构建号和提交号，三者可以相互查询；推送 tag 触发发布，生成带校验和的 Release。
  4. 对任一制品或正在运行的服务，指出它来自哪次提交、哪个 PR、哪次构建，即回答 L-05 提出的问题：线上运行的是哪次提交？

本实验对应 L-05 第 9～14 页从“源码与提交”到“发布”的五个节点，第 28 页为实验预告；CI 原则见 L-02 第 9～10 页。每完成一步，都可以用 L-05 的两个问题检验：这一步的产出物是什么？出现问题时能否回到上一个状态？

实验按“提出假设 → 施加变更 → 收集证据 → 分析 → 改进并复测”的顺序安排：

环节 本实验中的对应内容
假设 没有流水线时，无法确定制品来自哪次提交；引入 gate 和版本标识后可以确定

改进与复测 任务 4：找出现有测试无法发现的缺陷，补充测试后再次验证；任务 6：发布 v1.0.1 后回退到 v1.0.0，并复核 v1.0.0 的制品

3流水线全貌#

每个制品携带三个标识，L-05 第 13 页要求三者能够相互查询：

标识 取自 回答的问题
版本号 version tag，v1.0.0 去掉 v 得到 1.0.0 兼容性承诺，面向用户
构建号 build_no github.run_number 第几次构建，面向流水线
提交号 commit github.sha（在 main 或 tag 上构建时） 对应哪一份源码，面向开发者

这三个标识写在制品中的 BUILD_INFO 文件里。示例服务运行时，也可以通过 GET /version 或 -version 参数查询。

BUILD_INFO 中另有一行 run_id，取自 github.run_id。构建号在每个工作流中各自从 1 开始计数，ci 和 release 都有各自的第 1 次运行，仅凭构建号无法区分是哪个工作流的哪次运行。run_id 在整个 GitHub 范围内唯一，trace.sh 据此直接给出该次运行的链接。

分支模型#

L-05 第 10 页指出，分支模型的具体做法在实验中说明。本实验的约定如下。

本实验采用主干开发（trunk-based development）。main 是唯一的长期分支，并始终处于可发布状态。每项改动从 main 创建一个短期分支，在一两天内通过 PR 合并回 main，合并后删除该分支。发布不单独创建 release 分支，而是直接在 main 的某个提交上打 tag。合并方式采用 squash：一个 PR 在 main 上只保留一个提交，其标题末尾带有 PR 编号，追溯时可由提交号找到对应的 PR。

另一类做法是长期分支模型，例如 GitFlow：除 main 外还长期维护 develop 分支，功能分支、release 分支和 hotfix 分支各有用途。它适用于发布周期长、需要同时维护多个版本的软件。其代价是分支存续时间长、合并晚，冲突和集成问题直到合并时才暴露，难以做到 L-02 所述的“每人每天向主干提交”。

主干开发同样有代价：测试必须可靠，否则 main 很快会失去可发布状态；改动须拆分得足够小；未完成的功能须置于功能开关之后才能合入（L-05 第 16 页）。squash 合并使 main 的历史保持线性，但分支上原有的各个提交只保留在 PR 页面中，在 main 上不可见。

任务 3：merge gate约 30 分钟#

merge gate 即 L-05 第 12 页所说的合并门禁。进入 Settings → Rulesets → New ruleset → New branch ruleset（Rulesets 在左侧菜单中直接可见；界面文字以 GitHub 当前页面为准，规则的正式名称见官方文档 Available rules for rulesets）。新建一个作用于默认分支、状态为 Active 的规则集，Bypass list 保持为空，至少启用以下四条规则：

  • Restrict deletions：禁止删除分支。
  • Block force pushes：禁止强制推送。
  • Require a pull request before merging：合并前必须通过 PR。Required approvals 设为 1。GitHub 不允许作者批准自己的 PR，因此每个 PR 都须由另一位组员审批。
  • Require status checks to pass：合并前必须通过状态检查，添加 ci。

审批是人工检查，ci 是自动检查，分别对应 L-05 第 10 页的两道门禁。

ci 已在任务 2 中运行过，添加检查时可以搜索到；搜索不到时先运行一次。如果 Settings 中找不到 Rulesets，或提示需要升级付费计划，请立即告知老师，不要将仓库改为私有，也不要自行付费。

任务 4：gate 演练约 60 分钟#

本任务分两轮。第一轮验证 gate 能拦住测试可以发现的缺陷；第二轮找出测试无法发现的缺陷，补充测试后，再验证 gate 能否拦住它。

第一轮：失败、修复、放行。

  1. 从 main 创建分支，做一个有意义的小改动，例如为 conflict_test.go 增加一个用例；并在同一个提交中有意引入一个会导致测试失败的缺陷。统一示例可以修改 conflict.go 中的 weeksOverlap，使单周班与双周班被判为冲突，即 L-05 课程实践第 3 题的场景。使用自己项目的组自行设计缺陷。
  2. 推送分支并发起 PR。ci 失败后合并按钮变为不可用，鼠标悬停时显示类似 “Merging is blocked due to failing merge requirements” 的提示（以实际文字为准）。记录这次失败运行的链接，以及发起 PR 和 ci 给出结果的时间。
  3. 在同一分支上追加修复提交，ci 重新运行并通过。记录链接和时间。
  4. 请另一位组员审批，然后 squash 合并，观察 main 上的 push 运行，记录链接和合入时间。合并前先修改 PR 标题：它将成为 main 上该提交的标题，默认取分支第一个提交的说明。若不删去“引入缺陷”之类的字样，它将永久保留在 main 的历史中。

第二轮：补充测试并复测。

  1. 阅读 conflict.go 和现有测试，找出一个现有测试无法发现的缺陷：代码行为已被改错，make test 却仍然通过。
  2. 新建一个分支，只提交该缺陷，推送并发起 PR，确认 ci 仍然通过、gate 没有拦住它。此时不要合并。
  3. 在同一分支上补充一个能发现该缺陷的测试，推送后 ci 应当失败。
  4. 撤销该缺陷，ci 通过后经审批合入。squash 之后，main 上只增加了一个新测试。
检查点

LAB1.md 第 3 节包含两轮演练的全部运行链接，第 5 节包含第一轮的时间线；两个 PR 的页面上都能看到 ci 失败的记录。

5选做#

选做不影响必做部分的评分，仅用于加分，上限见第 7 节。

  • O1 容器镜像（需要 Docker）：
    • 内容：在 release.yml 中增加一个 job，用 Release 附件和仓库中的 Dockerfile 构建镜像（镜像中不重新编译），推送到 ghcr.io/<小写的仓库路径>。记录镜像摘要（digest）和运行容器的主机架构，并用摘要而非 tag 运行一次容器。
    • CPU 架构：镜像中放的是 Actions 构建的 linux/amd64 二进制文件，因此镜像也是 linux/amd64。在 arm64 主机（例如 Apple 芯片的 Mac）上运行时，Docker 会提示平台不匹配，需加 --platform linux/amd64 以模拟方式运行；能否运行取决于 Docker 的模拟支持，且速度较慢。多架构镜像不在本实验范围内。
    • 思考：发布 job 创建的 Release 为什么不会触发另一个工作流，以致镜像 job 只能写在同一个工作流中？GitHub Container Registry 的包默认私有，关联到仓库后通常继承仓库的可见性，请自行确认镜像能否匿名拉取。
  • O2 缓存对反馈时间的影响：setup-go 默认开启缓存，因此各组的 ci 实际上一直在使用缓存。先写下预期：示例没有第三方依赖，缓存能节省多少时间？然后发起一个 PR，将 setup-go 的 cache 设为 false 作为对照（该 PR 不合并），用 Re-run all jobs 反复运行。有缓存和无缓存各至少运行 5 次，全部列出，并说明时长波动的来源和结论的局限。共享 runner 的负载会使单次时长存在很大噪声。
  • O3 迁移到小组项目：主线使用统一示例的组，可以将同样的 gate 和发布流水线迁移到自己的项目上，并说明迁移中遇到的差异。

7提交与现场检查#

提交： 提交小组仓库的地址，并按已公布的组号规则写明组号；提交渠道另行通知。

评分以截止时刻 2026-10-26 23:59 为准：只计入此前合入 main 的内容和已发布的 Release，之后合入的 PR、新建的 Release 不计分。main 受保护，每次改动的合入时间均由 GitHub 记录。

检查结束且成绩公布之前，不要删除仓库、PR、Release 和 Actions 记录，也不要将仓库改为私有。主干上的 artifact 按任务 2 的设置只保留 14 天（未设置时默认 90 天），且须登录才能下载，因此长期证据以 Release 为准；Release 附件无需登录即可下载。

  3. 打开两轮 gate 演练的 PR，说明每一步发生了什么。

8恢复与清理#

  • 推送错误且尚未发布的 tag：先 git push --delete origin <tag>，再 git tag -d <tag>。
  • 已发布的版本号不删除、不复用。发布有误时，应再发布一个修订版本（例如 v1.0.2），并在旧版本的说明中写明问题。制品不可变，见 L-05 第 11、18 页。
  • 临时分支：PR 合并后自动删除；scratch/ 等分支用 git push --delete origin <分支> 清理。
  • 本地：make clean 删除 dist/（任务 6 下载的附件也在其中）；用 pgrep -a enroll-conflict 确认任务 6 启动的服务均已停止；完成 O1 的组用 docker rmi 删除本地镜像。
  • 证据按第 7 节的要求保留到成绩公布。

9测量与局限#

  • ci 的运行时长受共享 runner 负载的影响，单次数据噪声很大。应列出全部运行，不要只给出平均值，并说明样本量很小。
  • “提交到发布的间隔”借用了 L-05 第 7 页 DORA 的“变更前置时间”，但几个 PR 的样本不能代表真实团队的水平。
  • 工作流中的 Go 固定为 1.26.9，本地是各组自行安装的版本，两者可能不同。BUILD_INFO 中记录了 go= 版本，比较二进制哈希之前应先核对该项。
  • 版本固定到补丁号，构建环境才能复现；代价是 Go 发布安全修复时不会自动更新，需要人工修改。ubuntu-24.04 固定的是系统版本，GitHub 仍会定期更新镜像中的软件；actions/checkout@v7 也只固定了主版本，v7 之内的更新会自动生效，要完全固定须写到提交 SHA。这几处都是“固定”与“及时更新”之间的取舍。
